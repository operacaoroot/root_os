## O caminho de volta, com os dois lados

| o quê | onde |
|---|---|
| banco, antes de tudo | `/root/backups/mktos/pre-root-os-20260912-1236.dump` — 1,4 MB, 501 objetos, TOC conferido |

A imagem foi salva **em disco**, não só marcada com tag, por um motivo medido: o
cron `docker image prune -af --filter until=24h` roda todo dia às 00:46 e o `-a`
apaga imagem sem uso **independente de tag**. A `mktos-app:rollback` só
sobrevivia por estar em uso; assim que a nova subiu, ela ficou órfã.

```bash
gunzip -c /root/backups/mktos/imagem-pre-root-os-20260912.tar.gz | docker load
docker tag mktos-app:pre-root-os-20260912 mktos-app:latest
cd /root/build-root-os && docker compose --env-file /srv/marketing-os/.env \
  -f docker-compose.yml -f docker-compose.vps.yml up -d --no-build api web
```

**A migração NÃO desfaz.** Voltar o esquema é restaurar o dump.

## O que foi medido antes de tocar em produção

**Produção já tinha 17 migrações — e duas eram desta branch.**
`regua_porta_rastro` e `tripulacao`, de 29/08. O Syncthing levou os arquivos
quando a branch foi escrita, o container foi recriado em 01/09 e o
`prisma migrate deploy` do `command` as aplicou sozinho. O esquema estava
parcialmente à frente do código havia duas semanas. Nenhuma migração aplicada em
produção estava ausente da branch: não havia divergência.

**As 20 pendentes foram ensaiadas duas vezes sobre cópia de produção, na própria
VPS** — o dado nunca saiu do servidor:

1. SQL cru, uma migração por transação, `ON_ERROR_STOP=1`: as 20 em 5,2 s. A
   mais lenta foi `isolamento_por_linha`, com 437 ms.
2. `prisma migrate deploy`, de dentro da imagem real, sobre um segundo banco
   restaurado cru — e o arranque compilado subiu a aplicação inteira contra ele.

**A mina do "passo zero" não morde hoje, e a prova é empírica.** Depois das
migrações, 86 das 87 tabelas ficam com RLS e FORCE. Conectado como a aplicação
conecta (`mkt`) e **sem `app.org_id`**, a consulta enxerga 5.065 linhas em 42
tabelas: o dado de produção inteiro. `FORCE` alcança o *dono* da tabela, mas não
quem tem `BYPASSRLS` — e `mkt` é SUPERUSER. O papel restrito nasceu trancado
(`mktos_app`, `rolcanlogin = f`, sem senha).

**As migrações ARMAM o isolamento sem LIGÁ-LO.** Os três caminhos que consultam
sem empresa só quebram quando a conexão virar `mktos_app`, e essa virada não foi
este deploy.

## Uma exposição de segurança fechou de lado

Antes do deploy, `mktos_db`, `mktos_redis` e `mktos_minio` publicavam em
`0.0.0.0`: **o Postgres de produção aceitava conexão da internet.** Subir com o
overlay `docker-compose.vps.yml` recriou os três em `172.17.0.1`. O `--vps` não
só evitou abrir: **fechou** o que já estava aberto.

## O que mudou de propósito

**A porta da rua do produto nasce trancada** (`1b06de3`).
`POST onboarding/cadastro` é anônima por desenho — é o degrau 0. Sem
interruptor, qualquer pessoa que achasse a URL criaria empresa no banco de
produção, entraria por Google (que a rota provisiona, então a allowlist não a
alcança) e gastaria modelo na conta da casa. O teto de taxa limita a VAZÃO, não
o DIREITO. `ONBOARDING_ABERTO=nao` está efetivo no container.

## O que aconteceu depois: a VPS reiniciou

Por volta das 19:27 a máquina saturou (load 214) e reiniciou. **A causa foi um
redimensionamento**: ela voltou com 8 núcleos (eram 4), 31 GiB de RAM (eram 15) e
387 GB de disco (eram 193).

Duas coisas quebraram no reboot, e **nenhuma é do deploy**:

1. **`mktos_db`, `mktos_redis` e `mktos_minio` não voltaram.** Saíram com código
   255 junto com o host e ficaram parados — enquanto `mktos_api` e `mktos_web`
   voltaram. A API entrou em laço de reinício com `P1001: Can't reach database
   server at db:5432`. Subir os três resolveu: banco saudável em 30 s, API
   saudável em seguida, zero erro desde então.
   **Defeito de operação a consertar:** os três containers de infraestrutura não
   têm política de reinício que sobreviva a reboot. Os de aplicação têm.
2. **O Traefik perdeu a publicação das portas 80 e 443.** O serviço está `1/1`,
   o processo `traefik` está vivo dentro do container, o swarm é líder e a spec
   declara as duas portas em `PublishMode: host` — mas `docker port` no
   container devolve **vazio** e nada escuta em 80/443 no host.

### O segundo é maior que este projeto

**Todos os sites da VPS estão fora**, não só o ROOT OS: `tools.fullbpo.com`,
`n8n.fullbpo.com` e `operacaoroot.com` respondem 000 de dentro da própria
máquina.

E o ROOT OS está íntegro por trás disso — medido de dentro da VPS, sem Traefik:

```
web(4000) = 200   api(4001) = 200
painel    = 200   central   = 200   bio = 200
```

O conserto padrão é recriar a tarefa do serviço, sem editar configuração à mão:

```bash

```

Não foi executado: o Traefik atende a máquina inteira — FullBPO, n8n, Evolution,
Supabase — e mexer nele é decisão do dono, não de quem veio fazer um deploy.

## O que falta, com o comando de cada um

### 1. O ritual das permissões — a fila de aprovação está 403 para todo mundo

Produção tem 140 vínculos em `_RolePermissions` e **não tem** `aprovacoes.ver`
nem `aprovacoes.decidir`. O item "Aprovações" não aparece no menu de ninguém e
`GET /approvals/fila` responde 403 — Admin Master incluído. Com a porta em
`impor`, o que ela retiver fica preso sem tela para soltar.

**O script NÃO é aditivo:** realinha com `set:` e **revoga** vínculo feito à mão
que não esteja na tabela do código. Distribuição atual: Admin Master 35, Gestor
de Marketing 24, Diretor 17, IA/Serviço 14, Analista 14, Social Media 13,
IA/Ação 12, Financeiro 7, Consulta Limitada 4.

```bash
ssh vps 'cd /root/build-root-os && docker compose --env-file /srv/marketing-os/.env \
  -f docker-compose.yml -f docker-compose.vps.yml run --rm --no-deps \
  --entrypoint sh api -c "cd /app/apps/api && pnpm db:sync-permissions"'
```

Depois, todo mundo sai e entra — o que vai acontecer de qualquer jeito, porque a

### 2. A semente da política — duas capacidades faltam no catálogo

A política ativa é a v1 de 29/08, com **60 capacidades**; o código espera **62**.
A API sobe assim mesmo e avisa (medido: não lança), mas a porta recusa quem
invocar as duas que faltam.

O seed **recusa rodar sem autor e motivo escritos** — e são **duas categorias de
assinatura, não uma**, porque são duas decisões diferentes e uma não pode comprar
a outra. Acrescentar capacidade que a base não classifica é `CAPACIDADE_NOVA`
(não declarada vale R5, então liberar é afrouxar); mexer em nível, limite ou
seção do documento é `REBAIXAMENTO`.

```bash
ssh vps 'cd /root/build-root-os && docker compose --env-file /srv/marketing-os/.env \
  -f docker-compose.yml -f docker-compose.vps.yml run --rm --no-deps \
  -e POLITICA_CAPACIDADE_NOVA_AUTOR="pedro.magnago@fullbpo.com" \
  -e POLITICA_CAPACIDADE_NOVA_MOTIVO="<a decisão escrita, 10+ caracteres>" \
  --entrypoint sh api -c "cd /app/apps/api && pnpm db:seed:politica"'
```

Sem assinatura ele **não muda nada** e imprime o que faria — ensaio seguro, e é
por onde começar para saber quais são as duas. A prova de que pegou é a linha de
arranque dizendo **62 capacidades**.
